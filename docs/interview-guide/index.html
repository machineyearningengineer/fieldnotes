Three answers to know first

1 · Explain one request

“What happens when I press Research?”

The gateway checks access. The API saves the question, queues its task ID and returns quickly. A worker claims the task, retrieves sources, generates and checks claims, then saves the report. The browser follows saved progress and lets me inspect the citations.

2 · Explain one crash

“What if the worker stops?”

Its lease eventually expires. Another attempt can claim the task with a newer epoch and reuse saved checkpoints. The old worker cannot write stale state if it wakes up. If a paid call’s outcome is uncertain, its allowance stays reserved and the task may fail visibly rather than repeat the call.

3 · Explain the evidence distinction

“Supported—but does it answer me?”

Support asks whether a passage justifies a sentence. Coverage asks whether that sentence answers the question. A study saying a fabric is warm when dry can support that claim without answering which coat is warmer in rain. Fieldnotes labels supported background as related evidence when it cannot answer directly.

The six distinctions to remember

Queue / DB

The queue delivers the instruction. The database owns the task’s truth.

Lease / epoch

The lease says until when you may work. The epoch says which ownership generation may write.

Epoch / revision

Epoch protects worker ownership. Revision orders snapshots for readers.

Support / coverage

Support: does this passage justify the sentence? Coverage: does the sentence answer the question?

Status / outcome

“Succeeded” means processing finished. “Answered / partial / unanswered” describes the result’s usefulness.

Limit / bill

Spending controls restrict new work. Accounting tells you what the work ultimately cost.

What is unfinished?

Requirement gap: full cost per task. Search is measured, AI is estimated, shared hosting is not allocated.

Quality limitation: fixed searches sometimes find related papers without answering the exact question.

The core workflow has recorded end-to-end evidence. These limitations don’t mean every question is answerable or every requirement is complete.

The lifecycle

Queued → Running → Succeeded / failed

While running: searching → writing → checking. A completed report has a separate answer outcome.

1. Don’t create the same job twice

The browser submits an idempotency key: a label for this intended submission. The database records it with the owner and request content.

Retrying the same key and input returns the original task. Reusing that key for different input is a conflict. A new key can create a new task, even for the same question.

Why this exists

A request can succeed on the server while its response is lost. Without a saved key, a browser retry could buy the same research twice.

2. Save before handing off

The API saves the task, then asks the queue to deliver it. These are separate operations: there is a crash gap between them.

A scheduled reconciliation checks accepted work needing delivery and re-enqueues it. The task record preserves the intent to do the work.

3. Claim temporary ownership

A database transaction lets a worker claim an available task. A transaction makes the ownership decision atomic: competing claims cannot both win the same claim.

The lease lasts 60 seconds and is renewed every 15 seconds. If the worker stops renewing it, the task becomes available to another attempt.

4. Stop the old owner writing

Every successful claim increments the epoch, an ownership counter. Every task-state write must carry the current epoch and a valid lease.

A claims epoch 1A works, then freezes. Its lease expires.
B claims epoch 2B is now the valid owner.
A wakes up with epoch 1Its stale task-state write is rejected.

Lease = expiry time. Epoch = ownership generation. They work together; they are not interchangeable.

Does that stop a paid call already in flight?

No. Fencing protects authoritative writes. It cannot undo an external request already sent to Valyu or Gemini. That uncertainty is why the accounting ledger keeps reservations when charges are unknown.

5. Resume saved work

A checkpoint is durable output a later attempt can reuse: completed searches, a completed generated draft, check results and published block identifiers.

Published block keys stop replay from appending the same block twice. A partially streamed generation may fail with its draft retained rather than buy another generation.

Checkpoint is not a promise to recover everything

A crash can happen after a provider performs work but before its result is saved. The system cannot always know whether it was charged. Recovery stays bounded and may end in a visible failure.

6. Keep the reader moving forwards

A revision is the version number of the saved snapshot. The browser ignores older updates, so a delayed poll cannot replace a newer streamed result.

Report blocks build progressively. This is not a general document-edit history or a separate “rendition” system. The task snapshot revision orders the visible state.

What if something goes wrong?

Start with what the user sees, then explain the protection underneath.

“I click twice or retry.”

The same idempotency key and input return the original task. A new key is a new submission.

“I close the browser.”

The queued research continues. Reopening restores saved state while the session still grants access.

“The API saves, then crashes before enqueueing.”

Scheduled reconciliation finds accepted work needing delivery and re-enqueues it.

“A worker stops.”

Another attempt can claim after lease expiry and reuse saved checkpoints. Some interrupted or uncertain work fails visibly instead of being repeated.

“My progress connection drops.”

The browser reconnects or polls for the same saved snapshot. Revision checks keep older updates from replacing newer ones.

“The papers don’t answer my question.”

The app labels the gap. Related findings are not presented as a confident answer.

“No acceptable claims survive.”

The task visibly fails, retaining available sources and draft progress. Processing failures are also shown explicitly.

Recover, reject or fail?

Invalid input → reject

Bad input is rejected before accepting a new task.

Lost delivery → reconcile

Accepted work needing delivery is re-enqueued.

Duplicate delivery → check ownership

An active lease or completed task prevents another worker from doing the same published work.

Confirmed-free retryable rejection → redeliver

Queue backoff owns retries. Saved completed work can be reused.

Uncertain cost, deadline or invalid report → fail visibly

Keep sources and available draft progress. Unknown charges stay reserved.

Unsupported claim → withhold

A bad candidate claim need not invalidate every good claim. Fatal structure or identity errors can still fail the task.

Say this

“Delivery can happen more than once. I use idempotent acceptance, transactional ownership, fenced writes and checkpoints to avoid duplicate or stale publication. I don’t claim exactly-once execution of paid external calls.”

One request, in order

From question
to checked answer.

“I want to know whether sodium-ion lasts longer than LFP in grid storage—and see what backs up the answer.”

Browser → Vercel

I ask my question.

I choose Compare, name the alternatives and press Research.

Behind it: the browser sends the question and an idempotency key. Vercel checks my session and forwards the request using its Google identity.

What is the gateway?

Server code on Vercel between the browser and the private Google API. It is called a backend-for-frontend, or BFF. It verifies access; it does not perform the research.

API → database → queue

My task appears.

I see “queued” rather than waiting for the whole answer.

Behind it: the API validates the input and admission limits, saves the task in Firestore, asks Cloud Tasks to deliver its ID, and returns that ID.

What if it crashes between saving and enqueueing?

The saved task survives. Scheduled reconciliation recovers accepted work needing delivery. The user does not have to keep the browser open.

Queue → worker

The research starts.

The state changes to searching.

Behind it: Cloud Tasks makes an HTTP request to the worker. The worker claims the task with a lease and epoch before doing work.

Is a worker watching the queue all day?

Not in this production setup. The queue pushes an HTTP delivery to the worker. Local synthetic mode uses a different local dispatcher.

Worker → Valyu

I see what it searched.

The search trail and sources arrive.

Behind it: Compare runs an academic query for each alternative and a broader comparison query. Discover uses one broad query and one academic query for limitations. Searches run concurrently.

Each search requests up to three results; the merged set is capped at eight. Text, metadata, query provenance and usage are saved.

Source text → labelled passages

The evidence is prepared.

There is nothing I need to do.

Behind it: code retains bounded, question-focused excerpts and divides them into labelled passages. Scientific Compare findings must use eligible research records. Ordinary web results can remain visible as sources.

Why not send every full document?

Bounded excerpts control input size, storage and cost. The trade-off is missing context. Source eligibility is also not proof of scientific quality or peer review.

Worker → Gemini

An answer is drafted.

The system is working out what it can say.

Behind it: Gemini proposes a short plan of the question’s parts, then factual claims pointing to source and passage IDs. Code owns the quoted text and citation links.

Validation → support → coverage

Checked blocks appear.

I can begin reading a visibly provisional report.

Behind it: code checks identifiers and numerical anchors. A separate model request assesses whether the passage supports each whole claim and which question parts it answers. Acceptable blocks are saved and sent to the reader.

Generation and checking can overlap. The site publishes saved checked blocks, not a pretend typing animation.

Final checks → saved outcome

I get an honest result.

It says answered, partly answered, not directly answered—or visibly failed.

Behind it: final validation checks the assembled report. The backend saves the report, outcome and usage. A processing success can still have an unanswered outcome.

Saved evidence → reader

I check a citation.

I open the supporting passage and original source.

Behind it: the source card uses the task’s saved evidence. Closing and reopening the page restores saved state while my session still grants access.

The thread through it all

The database saves the truth. The queue delivers work. The worker makes progress. The browser shows the saved result.

Evidence & presentation

True to the passage.
Useful to the question.

Those are separate checks. A factual sentence can still be irrelevant.

An everyday example

“Which coat keeps me warmer in the rain?”

A source says: “This fabric is warm when dry.”

Support: the source supports the statement about dry fabric.
Coverage: it does not answer the wet-weather comparison.

Illustrative analogy, not a Fieldnotes research result.

Support

“Does this exact passage justify every part of this sentence?”

Check the entities, numbers, conditions, comparisons and scope.

Coverage

“Does this supported sentence answer a requested part of the question?”

Related background is not a direct answer.

What the model is allowed to write

A claim is one proposed factual statement. A passage is a labelled piece of retained source text.

Claim: a narrowly scoped finding.
Source ID: which source?
Passage ID: which piece of that source?

Code looks up the selected passage and builds the citation from the saved source URL. The model does not get to invent the quoted text or citation destination.

The checks, in order

IDENTITYDo the source and passage exist?Check that the passage belongs to the selected source.
NUMERICAL GUARDAre the claim’s numbers in that passage?A cheap rejection rule. It does not prove the units or interpretation are right.
SUPPORTDoes the passage support the whole sentence?Supported claims may continue. Partial, contradicted or insufficient claims are withheld.
COVERAGEWhich requested parts does it answer?A supported laboratory finding may not answer a real-world grid comparison.

How does it know what needs answering?

Gemini proposes a small coverage plan: up to five aspects of this question. The code calls these facets.

For a battery comparison

Facet 1: compare cycle life in the requested setting.
Facet 2: compare low-temperature performance.

The checker returns the facet IDs each claim actually answers. Code uses the accumulated coverage to choose an outcome.

The plan and checker are model judgements. They can miss something or agree on the same mistake. They do not certify completeness or scientific truth.

Why “succeeded” can mean “unanswered”

Answered

Accepted claims cover the required parts of the model-generated question plan. This is not proof the literature is complete.

Partial

Accepted answering claims leave required parts unresolved.

Unanswered

Supported related claims survive, but none directly answers the question. They appear as related evidence with an explicit warning.

Failed

No acceptable claims survive, or the workflow cannot finish safely. Sources and any saved draft remain available.

Traceability: follow a claim back

Traceability means being able to follow a report statement to the particular passage and source behind it.

A sentence in the reportWhat is being claimed?
Its citation and source cardWhich source, author/date and retained passage?
The original sourceOpen the publication to inspect context beyond the retained excerpt.

The search trail separately shows how the source was found. Traceability makes a claim inspectable; it does not prove the source or the model’s interpretation is correct.

What the reader receives

SSE means Server-Sent Events: a one-way stream of saved snapshots. The browser displays checked blocks as they are saved. Polling is the fallback when streams stall or disconnect.

Both transports use the same snapshot and forward-only revisions. The outline, citations and source panels should agree because they reflect that shared server state.

Source cards show metadata and evidence. The search trail shows the queries, so the user can judge a retrieval gap rather than assume no research exists.

Don’t overclaim: a valid URL is not evidence of support. A supported statement is not necessarily relevant. An eligible paper is not necessarily correct or peer reviewed.
Architecture & scale

Same work.
Different hosting.

Start with the VPS you know. Then swap in the managed Google services.

Required: Google Cloud backend and Vercel frontend.
Chosen: Cloud Run, Cloud Tasks and Firestore. A Google VM with Postgres was also an option; the brief did not require serverless.

A VPS is a rented virtual server. Serverless still runs on servers; the provider manages their allocation. You still own application correctness.

Read down the main request path. The API and worker both read/write the database; the database is not another queue step. Progress returns from saved state through the API and gateway to the browser.

How to draw this in an interview

Draw Browser → Vercel gateway → API across the top. Put Database beneath the API. Then API → Queue → Worker. Connect the worker to Database, Valyu and Gemini. Add a return arrow from API to Browser labelled “saved snapshots”. Add Scheduler → API labelled “recover undelivered work”.

That captures ownership and data flow without drawing every request.

Why these services?

Use managed delivery and storage, then spend the project’s effort on reliable research and inspectable evidence. These are defensible choices, not the only possible stack.

Next.js on Vercel

Hosts the interface and server-side gateway.

Why it fits and the trade-off

Why: Vercel was required. Next.js lets the UI and its session gateway live together.

Trade-off: Some deployment-specific behaviour; another frontend framework could work.

Vercel gateway / BFF

Checks the browser session and calls the private Google API.

Why it fits and the trade-off

Why: Keeps privileged Google access on the server and gives the browser one application origin to use.

Trade-off: Adds another network hop and proxy layer.

Federated Google identity

Lets Vercel authenticate to Google.

Why it fits and the trade-off

Why: Avoids storing a long-lived Google service-account key in Vercel.

Trade-off: More involved initial identity configuration.

Cloud Run API

Accepts questions, returns task IDs and serves progress.

Why it fits and the trade-off

Why: Runs a normal container without managing a VM. Fits short HTTP requests and low, bursty traffic.

Trade-off: Cold starts and platform limits; not inherently better for steady workloads.

Separate Cloud Run worker

Performs the slow research.

Why it fits and the trade-off

Why: Research continues independently of the submission request. Worker permissions and capacity can differ from the API’s.

Trade-off: Two services to deploy and observe.

Cloud Tasks

Delivers task IDs to the worker over HTTP.

Why it fits and the trade-off

Why: Gives managed delivery, backoff and concurrency control. The worker doesn’t need an always-running queue listener.

Trade-off: Delivery can repeat, so application-level deduplication and ownership checks remain necessary.

Firestore

Saves task state, ownership, checkpoints and reports.

Why it fits and the trade-off

Why: A task is naturally a document; transactions support safe acceptance and worker claims. No database server to operate.

Trade-off: Document-size limits, read/write charges and contention on frequently updated records. Less suited to relational queries.

Cloud Scheduler

Periodically triggers reconciliation.

Why it fits and the trade-off

Why: Repairs the gap where the task was saved but never successfully queued.

Trade-off: Recovery can wait for the next scheduled run.

Secret Manager

Supplies the Valyu key to the worker.

Why it fits and the trade-off

Why: Centralises secret access and keeps the key out of browser code and Git.

Trade-off: Requires permissions and secret lifecycle management.

Valyu Search + official SDK

Retrieves source text and metadata.

Why it fits and the trade-off

Why: Required by the brief. Provides material the app can cite and inspect, rather than just links.

Trade-off: External latency, cost and retrieval coverage constrain answer quality.

Gemini through Vertex AI

Generates structured claims and checks their evidence.

Why it fits and the trade-off

Why: Keeps model access within Google identity and infrastructure. The selected Flash model fits a bounded, latency-conscious workflow.

Trade-off: Model judgement can be wrong; provider latency and quotas remain external dependencies.

Cloud Trace

Records timings across research steps and calls.

Why it fits and the trade-off

Why: Helps distinguish queue delay, search latency, generation latency and checking time.

Trade-off: Instrumentation and operational overhead; tracing alone doesn’t establish answer quality.

Why these application choices?

The cloud products deliver and store work. These code-level rules make its behaviour reliable and inspectable.

What to acknowledge

Shared contracts and OpenAPI

Keep requests, snapshots and errors consistent and make the API inspectable.

What to acknowledge

Contracts must evolve carefully; generated types don’t replace runtime checks.

Provider adapters

Separate research rules from Valyu, Gemini and Firestore details. This also enables synthetic local providers.

Extra abstraction; keep it small rather than building a general framework.

Makes success and typed failure handling explicit in those boundaries.

It adds a concept to learn. Most worker orchestration still uses ordinary async code; Effect isn’t what makes processing durable.

SSE with polling fallback

Progress is one-way, from server to browser. SSE delivers saved updates promptly; polling handles disconnected or stalled streams.

What to acknowledge

Connections and database reads become their own scaling concern.

Saved snapshots with revisions

Refresh and reconnect restore one coherent backend state. Revisions prevent older responses replacing newer ones.

What to acknowledge

Sending complete snapshots can become expensive as reports grow.

Leases and epochs

Leases allow recovery after an owner disappears; epochs reject writes from a superseded worker.

What to acknowledge

They protect task state, not external calls already sent.

Why this design?

“The brief required Google Cloud, and this is a small, bursty, asynchronous workload. Cloud Run, Cloud Tasks and Firestore reduce the infrastructure I need to operate. On a VPS I could run the same API and worker, perhaps with Postgres for state and jobs, but I’d own more of the process supervision, capacity and recovery setup. The reliability rules would still be necessary.”

Could Receipts use this?

It could use managed containers and push-based job delivery while keeping Postgres. Moving to Cloud Run does not require moving to Firestore. Relational queries and constraints are a reason to retain Postgres.

SKIP LOCKED helps competing workers claim different database rows. If the claim transaction ends before a long external call, durable ownership and recovery still need a design. It is not automatically the same guarantee as epoch fencing.

Read-heavy or write-heavy?

Executing research: many meaningful writes

Acceptance, claim, lease renewal, search results, reservations, receipts, draft/check checkpoints, report blocks and completion.

Focus now: provider waiting time, useful-answer quality and bounded spending. There is no measured production read/write ratio to quote.

Viewing research: read-heavy

Loads, subscriptions, updates, reconnects and polling. Many people watching can create more read/connection pressure than the worker count suggests.

Focus as usage grows: reads per viewer, active connections, payload size, and caching completed authorised reports.

Subtle point: conditional GET may save response bytes while still requiring a database read to discover the current revision.

What gets slow first?

A bottleneck limits throughput. Contention means operations compete over the same resource.

1. Worker slot and provider latency

Pressure: one slow call occupies the only delivery slot.

Measure: queue age, task duration, provider latency and rate-limit responses.

Expand: raise queue concurrency and worker capacity together, within quotas and spending limits.

2. Shared admission and budget records

Pressure: transactions compete to update the same global records.

Measure: transaction retries and latency.

Expand: allocate bounded budgets/capacity across tenants or partitions without letting the allocations exceed the total.

3. Progress writes and growing artifacts

Pressure: repeated task writes and large snapshots increase database and transfer work.

Measure: writes per task, payload sizes and contention.

Expand: reduce redundant updates; keep important checkpoints; move large immutable artifacts to object storage.

4. Viewers and reconnects

Pressure: streams and polling grow independently from research execution.

Measure: connections, reads per viewer and reconnect bursts.

Expand: share update distribution and cache authorised immutable results by owner, task and revision.

Sizing example, not a benchmark

10 arriving tasks per minute × 30 seconds each ≈ 5 running tasks on average. Allow headroom for variance. More workers help only if providers, database and budget can support them.

Synthetic load testing and a measured production capacity limit remain unestablished. Leases protect ownership; they are not backups or disaster recovery.

What works & what remains

A working flow.
Two honest limits.

The biggest unfinished requirement is full job cost. The biggest quality weakness is retrieving evidence that answers the exact question.

1. “What did that job really cost?”

Imagine ordering food: you know the food price, but haven’t added delivery and service charges.

What is recorded today

Search: measured Valyu deductions.
Model: estimates from reported tokens and configured rates.
Hosting: shared charges, not allocated to individual tasks.

That is partial provider accounting, not the complete cost of delivering each job.

Some billing evidence arrives later. Infrastructure serves several tasks and viewers, so it needs a clear allocation rule rather than pretending every charge belongs to one task.

Say this

“I record search charges and estimate model usage per task. Full cost accounting is unfinished because I haven’t reconciled estimates against billing or allocated shared infrastructure costs. The next step is billing reconciliation.”

What would completing it involve?

Read the billing export, associate attributable charges with task references, reconcile model estimates, and allocate shared costs using declared measures such as runtime, writes and deliveries. Report unallocated costs explicitly. The README documents this direction; implementation and attribution need verification.

Spending control is already separate

The ledger reserves allowance before each provider call, then settles from its receipt. Unknown charges keep their reservation.

Current research envelope

USD0.10 provider allowance per task.
At most 12 provider operations.
At most 3 searches and 8 retained sources.
Five-minute task deadline.
One concurrent queue delivery, with bounded attempts.

These are configured controls, not a claim that all infrastructure costs are hard-capped. A provider overrun can stop further work but cannot undo an incurred charge.

2. “Did those papers answer me?”

A paper about warm fabric in dry weather may be accurate, but it doesn’t answer which coat is warmer in rain.

Fieldnotes sometimes retrieves evidence with that kind of mismatch. It uses a small, fixed set of searches and does not automatically search again for missing parts.

Say this

“Bounded searches can return related evidence without a direct answer. I label that honestly. I’d improve and evaluate retrieval first, then consider a targeted follow-up search for missing parts.”

The current saved Compare example reports related sodium-ion research but does not establish the requested grid-storage comparison. Honest abstention is valuable; it still leaves the user without the answer they wanted.

Why was follow-up search left out?

The brief allowed at most one implemented research-orchestration technique. The chosen technique was claim-to-passage grounding. Adaptive follow-up would also need a defined budget and another synthesis pass within or beyond the current operation limits.

This explains the scope choice. It does not excuse the separate cost-accounting requirement gap.

Three next priorities

1. Complete accounting

Reconcile bills, attribute direct charges, allocate shared costs and expose the remainder.

2. Improve answer usefulness

Evaluate query changes, source selection and targeted follow-up against useful-answer rate, evidence quality, latency and cost.

3. Strengthen evidence and operations

Broaden quality evaluation, exercise viewers/reconnects with synthetic providers, and define retention, deletion and recovery.

Already improved

Saved step progress, one cost ledger, queue-owned retries, explicit outcomes, trace spans, an offline claim-check gate, broader scholarly retrieval and stricter evidence eligibility are already recorded as landed.

The offline set contains ten reviewed claim/passage cases. They passed the recorded run; a deliberately lax checker failed two. Coding-agent-selected cases are useful regression evidence, not an independent scientific benchmark.

Other limits worth knowing: anonymous demo sessions lack account recovery and automatic report deletion. Discover’s explanation/evidence intent is model-selected, which affects source eligibility. The scaled system is described, not load-proven.
